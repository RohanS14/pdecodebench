`data/`: Datasets and descriptions of data. See <a href='https://github.com/RohanS14/pdecodebench/blob/main/data/descriptions/data_spec.txt'>data_spec.txt</a>
- **Current: the jul28 release — six CSVs plus an ablation file.** `merged_mod_jul28.csv` is the canonical eval
  dataset: 256 rows, 32 `gt_sample`s × 8 `mod_type`s. Balance: 64 rows per `pde_class`,
  32 per `mod_type`, 128 valid / 128 invalid.

  | File | Rows | Contents |
  |---|---|---|
  | `merged_mod_jul28.csv` | 256 | full 8-way `mod_type` expansion, both sources, + `source` column |
  | `human_mod_jul28.csv` | 128 | human source only |
  | `synthetic_mod_jul28.csv` | 128 | synthetic source only |
  | `merged_base_jul28.csv` | 64 | pre-expansion base, one row per (`gt_sample`, valid/invalid) |
  | `human_base_jul28.csv` | 32 | human source only |
  | `synthetic_base_jul28.csv` | 32 | synthetic source only |
  | `leak_ablation_jul28.csv` | 48 | **not** part of the eval set — 6 repaired samples x 4 invalid conditions x 2 `leak_variant`s (`widened` = original leaky code, `aligned` = repaired), for measuring the leak rather than only removing it |

  The 32 base problems come from two independently-tracked sources of 16 each. `CorrComm`
  and `NoComm_CorrVar` donors never cross the human/synthetic boundary, so `merged_*` is a
  straight concatenation of the two single-source files, not a fresh build over all 32.
- `equations_jul28.csv` — **Experiment 2 Part II modality.** One symbolic PDE per
  `gt_sample` in three notations (unicode / LaTeX / ASCII), so cross-modal retrieval can
  separate matching the *physics* from matching the *notation*. Generated by
  `datagen/build_equations.py`, never hand-edited. Each row carries the evidence it was
  derived from plus `needs_review` / `verified_by`: this file is the physics ground truth
  for every cross-modal number, so a wrong equation corrupts results in a way no
  downstream statistic can detect. **1 of 32 rows currently awaits sign-off**
  (`NavierStokes_3`).
- `Physics_Code_HumanGen.xlsx` — source workbook for the human half.
- `archive/` — all pre-jul28 versions (`pdedata.xlsx` through `pdedata_clean_v5.xlsx`, plus
  `physics_code.xlsx`). Kept for reference; not read by any current build script.
- `descriptions/dataset_overview.md` — schema, column reference, version history, and
  known limitations. Two open items as of 2026-07-31: `num_lines` is +1 on 80/256 rows
  (all synthetic — a trailing-newline counting difference between the two parsers; `code`
  and `num_char` are correct), and `NavierStokes_5`/`_6` are labelled `navier-stokes`
  while their governing equations are diffusion equations. Labels otherwise verified
  against code with no contradictions.

`datagen/`: Scripts for dataset corruption and augmentation.
- `build_jul28.py` — builds all seven jul28 CSVs end to end. Deterministic: two consecutive
  runs produce byte-identical output.
- `parse_humangen.py` — parses and repairs the human half from `Physics_Code_HumanGen.xlsx`
- `parse_newcode.py` — parses the synthetic half from `data/newcode_jul28.txt`
- `corrupt_comment.py` — `CorrComm` / `CorrComm_Invalid` donor-comment injection
- `augment_foobar_vars.py` — `NoComm_CorrVar` / `_InValid` AST variable obfuscation. Renames
  every author-chosen identifier and nothing else: `visit_Call` moves a same-module callee's
  `keyword.arg` in lockstep with its renamed parameters, while library kwargs
  (`np.zeros(shape=…)`) are always left alone since they are the library's API.
- `audit_dataset.py` — fast balance/integrity check; runs inside the build, also a CLI
- `full_audit.py` — 49 structural and semantic checks (condition semantics, donor
  constraints, label leakage, cross-condition program identity). **49/49 as of 2026-07-30**
- `full_audit_exec.py` — executes all 256 rows and verifies that a `gt_sample`'s four
  surface conditions produce identical numbers
- `build_equations.py` — builds `data/equations_jul28.csv` (Experiment 2 Part II).
  Dimensionality and physics are read from the solver source, not from `pde_class`.
  Deterministic: re-running produces a byte-identical file. Four traps it now handles,
  each of which produced a wrong equation before being fixed: a two-axis array may be a
  **time history** of a 1D field rather than a 2D domain (`u = np.zeros((nt, nx))`);
  `alpha = np.maximum(np.abs(u[:-1]), np.abs(u[1:]))` is Rusanov numerical dissipation,
  not viscosity; viscosity can be zeroed by tuple assignment (`L, nu = 2.0, 0.0`); and
  `\bpsi\b` does not match `psi_hat`, because underscore is a word character.
- `extract_trajectories.py` — executes all 256 rows in a sandboxed subprocess and records
  a physical summary, a label-free text rendering of the dynamics, and the valid-vs-invalid
  **numerical divergence**. The divergence is what lets Experiment 2 ask whether `‖Δh‖`
  tracks the size of the *real physical error* rather than the size of the code edit.
  CPU-only; run via `sbatch/run_build_modalities.sbatch`, never on a login node.
- `derive_invalidity_change.py` — derives *how* each invalid variant was made invalid from
  the valid↔invalid diff, and separates the physical error from incidental drift

Run the audits as batch jobs, never on a login node — `sbatch/run_dataset_audit.sbatch`
(CPU-only, `cpu_short`) runs both. `NavierStokes_3` additionally needs FFTW3 and a real MPI,

- `build_v3.py` / `build_v4.py` / `build_v5.py`, `patch_*.py`, `remove_assertions.py` —

`sbatch/`: SLURM job scripts. Cluster layout follows
`/scratch/ehb7466/projects/PROJECTS.md`: code in `$HOME/pde-llm-eval` (synced from this
desktop repo), results on scratch under `projects/pde-llm-eval/{outputs,logs}`, venv at
`/scratch/ehb7466/envs/pdecodebench`.

> **Call the venv interpreter by absolute path — never `source .../activate`.**
> That venv was created at `/scratch/ehb7466/venvs/pdecodebench` (plural `venvs`) and
> later moved to `.../envs/pdecodebench`. `bin/activate` still exports the original
> `VIRTUAL_ENV`, so sourcing it prepends a directory that no longer exists and leaves
> `python` resolving to `/usr/bin/python`, which has no numpy. The failure is silent —
> `activate` returns 0 and the job dies at import with elapsed `00:00:00` (this killed
> job 15050504). Every script here now uses:
> ```bash
> PY="$VENV_PATH/bin/python"
> [ -x "$PY" ] || { echo "venv interpreter not found: $PY"; exit 1; }
> ```
> Worth fixing at the source (recreate the venv in place, or patch `VIRTUAL_ENV` in
> `bin/activate`) since any job that activates it hits the same trap.

> **Never verify package versions on the login node — they differ from the compute
> node.** `$VENV_PATH/bin/python` resolves to a *different interpreter* depending on
> where it runs, because `bin/python3` symlinks to `/usr/bin/python3` and the node
> images differ. The venv carries four separate site-packages trees
> (`lib/python3.9`, `lib/python3.12`, `lib64/python3.9`, `lib64/python3.12`):
>
> | | interpreter | transformers |
> |---|---|---|
> | login node | Python 3.12.13 | 5.14.1 |
> | **compute node (what jobs use)** | **Python 3.9.21** | **v4** |
>
> Measured from job 15051200's own log, not inferred. Practical consequences:
> `torch_dtype=` is still correct on compute (it became `dtype=` only in v5), so both
> extractors try `dtype` and fall back to `torch_dtype` on `TypeError` — without that
> fallback the run would have failed. Anything version-sensitive must be checked by
> submitting a job, never from the login shell.

`probe/`: Probing experiments on model hidden states (Experiments 2 and 5).
- `extract_hidden.py` — one forward pass per row, saves per-layer `mean_pool` (mean over
  code tokens only) and `last_tok` hidden states to an NPZ. Reads jul28 CSVs via
  `eval/dataset_io`. Stores **float32**: Experiment 2 differences two forward passes on
  nearly identical inputs, and at `‖Δh‖/‖h‖ ~ 1e-2` float16 would leave 1–2 significant
  digits and the cosines would measure rounding error.
- **Experiment 2 — World Model.** Are physical defects represented consistently across
  descriptions? `Δh = h(invalid) − h(valid)` for each solver under each of the 4 surface
  conditions; the question is whether the same edit moves the representation the same way
  under different descriptions. Plan: `probe/plans/exp2_world_model.md`.
  - `world_model_delta.py` — Δh construction, control battery, permutation test → tidy
    long CSV. The headline numbers are the within-vs-cross-solver `gap` and `match_acc`
    (top-1 defect retrieval, chance 1/32), **not** `within_cos`, which a single global
    "broken code" direction inflates to ~0.5 with no solver-specific structure present.
  - `viz_world_model.py` — self-contained Plotly report. Cross-model panels use relative
    depth `ℓ/(L−1)`; the roster spans 28–65 layers, so raw layer index is meaningless.
  - Validated on synthetic ground truth before any compute — see
    `tests/test_world_model_delta.py`.
- **Experiment 2 Part II — physics vs. code.** Part I varies only how a fixed program is
  *described* (comment-stripped source is byte-identical across three of its four
  conditions; the fourth is AST-isomorphic), so a purely syntactic representation would
  ace it. Part II adds the orthogonal axis. Plan §13–§16.
  - `code_similarity.py` — the nuisance regressors that make a physics claim possible:
    token Jaccard (surface), identifier-stripped AST n-grams (structure), length.
  - `physics_vs_code.py` — does `pde_class` explain representational distance *after*
    partialling out code similarity? Mantel permutation over **solver identity**; the 496
    pairwise distances are not independent and permuting them directly would inflate
    every p-value.
  - `extract_modality_hidden.py` — embeds the equation and trajectory modalities under a
    neutral prompt that names neither the PDE class nor the numerical method.
  - `cross_modal.py` — equation ↔ code ↔ trajectory retrieval, scored **within
    `pde_class`** (chance 1/8) as well as globally, because 4-way category matching can
    solve the global version. Lexical overlap is measured and partialled out.
  - `geometry_battery.py` — intrinsic dimensionality of the physics vs. code manifolds,
    linear-vs-kNN decodability of `pde_class`, cross-class transfer of the validity
    direction, and an anisotropy baseline (unlike Part I, nothing here differences).
- `plans/` — experiment descriptions and TODOs. `exp2_world_model.md` is the current
  Experiment 2 plan (Parts I and II). `experiment_description.md` and `TODO.md`
